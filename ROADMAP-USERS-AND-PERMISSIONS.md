# Дорожная карта: пользователи кафедр, права по группам и персональная отмена

Дата: 27 сентября 2026 года.

Статус: реализовано 27 сентября 2026 года. Результаты проверки и закрытые риски
зафиксированы в `IMPLEMENTATION-AUDIT-USERS-2026-09-27.md`.

## 1. Назначение и обязательные правила

Система получает учётные записи сотрудников кафедр. Все вошедшие сотрудники видят рабочее расписание целиком, но могут изменять только занятия разрешённых им групп. Гости видят опубликованное расписание без права записи.

Обязательные правила, следующие из согласованного замысла:

1. Администратор создаёт пользователя, задаёт логин, пароль и группы, расписанием которых пользователь управляет.
2. Группы назначаются через выбор кафедр, через ручной выбор отдельных групп или обоими способами одновременно.
3. Право изменения занятия определяется его группами. Кафедра преподавателя, принадлежность аудитории и открытый вид расписания не дают и не отнимают это право.
4. В расписании аудитории и преподавателя пользователь редактирует занятия своих групп. Остальные занятия остаются видимыми, выделяются как недоступные для изменения и открываются только для чтения.
5. Добавить занятие можно из любого представления расписания. Создавать его можно только для разрешённых групп.
6. Журнал переносов общий для всех вошедших пользователей. В каждой новой записи указан автор.
7. Отмена адресуется конкретному действию. Перенос другого пользователя не меняет цель уже показанной кнопки «Отменить».
8. Сервер проверяет разрешения независимо от интерфейса, непосредственно перед записью.

Термин «своя группа» ниже означает группу, входящую в текущий набор разрешений пользователя. Это не обязательно группа его кафедры: она может быть назначена вручную.

## 2. Решения, фиксируемые для первой версии

Следующие пункты закрывают случаи, которые не были отдельно определены в переписке. Для реализации принимаются именно эти решения; менять их молча внутри отдельных задач нельзя.

| Вопрос | Решение |
|---|---|
| Разрешения на преподавателей и аудитории | Отдельных разрешений нет. Они являются общими ресурсами расписания |
| Несколько кафедр у пользователя | Разрешены |
| Кафедры плюс ручные группы | Объединение двух наборов, без дубликатов |
| Исключение одной группы из выбранной кафедры | В первой версии не поддерживается. Для такого набора используется ручной выбор групп |
| Новая группа в разрешённой кафедре | Доступ появляется после явного закрепления группы за кафедрой администратором |
| Группа без кафедры | Доступна для записи только по прямому ручному назначению |
| Пользователь без разрешённых групп | Может войти, просматривать и экспортировать расписание; изменять его не может |
| Занятие со своими и чужими группами | Целиком только для чтения; разделение потока при редактировании не выполняется |
| Занятие без групп | Обычному пользователю недоступно для создания и изменения |
| Публикация изменений | Только администратор; сотрудник изменяет рабочее расписание |
| Самостоятельная регистрация | Не предусмотрена |
| Создание дополнительных администраторов через интерфейс | Не входит в первую версию; создаваемые пользователи имеют роль редактора расписания |
| Удаление учётной записи | Вместо удаления используется блокировка, чтобы сохранить авторство истории |
| Кто может отменять чужие действия | Администратор через явно выбранную запись журнала. Обычный пользователь — только свои действия |
| Отмена прочих операций | Персональная адресная отмена переносов входит в первую версию. Существующий общий откат других изменений обычным пользователям не предоставляется |

## 3. Роли и источники данных

### 3.1. Гость

- Просматривает опубликованный снимок, а не рабочие изменения.
- Сохраняет существующие возможности печати и экспорта в пределах настроек гостевого доступа.
- Не создаёт и не меняет занятия, даже если в старых настройках включено гостевое редактирование.
- Не получает список пользователей, служебный журнал безопасности, хеши паролей или правила доступа.

### 3.2. Редактор расписания

- После входа работает с текущим рабочим расписанием.
- Просматривает расписания любых групп, преподавателей и аудиторий.
- Редактирует занятия только в пределах разрешённых групп.
- Видит общий журнал переносов и авторов действий.
- Меняет собственный пароль с подтверждением текущего пароля.
- Не управляет пользователями, справочниками, кафедральной принадлежностью и системными настройками.

### 3.3. Администратор

- Сохраняет существующие административные возможности.
- Управляет пользователями и правами, подтверждает принадлежность групп кафедрам.
- Может выполнять операции над занятиями любых групп.
- При отмене чужого переноса явно выбирает действие; автор отмены фиксируется отдельно от автора исходного переноса.
- Проверки занятости, актуальности данных и целостности при адресной отмене действуют и для администратора. Принудительный откат поверх новых изменений не входит в эту функцию.

## 4. Вычисление доступа

### 4.1. Принадлежность групп кафедрам

Для прав доступа используется одна явно сохранённая принадлежность группы кафедре, общая для формы назначения прав и серверной проверки. У группы может быть одна кафедра либо отсутствовать кафедра.

В текущем коде кафедра группы местами выводится из её названия. Такое вычисление разрешено только как предложение при первоначальной подготовке данных. Изменение имени, импорт расписания или смена состава занятий не должны незаметно менять права.

Порядок подготовки:

1. Собрать существующие кафедры и группы.
2. Показать администратору текущую сохранённую кафедру и вычисленную подсказку раздельно.
3. Разногласия и отсутствующие значения вывести отдельным списком.
4. Зафиксировать подтверждённую принадлежность. Неподтверждённые группы считать группами без кафедры для целей доступа.

Редактировать принадлежность может только администратор. Перед переносом группы в другую кафедру интерфейс показывает, какие пользователи получат и потеряют кафедральный доступ.

### 4.2. Формула разрешённых групп

`Разрешённые группы = группы подтверждённых выбранных кафедр ∪ группы, назначенные вручную`.

- Повторное попадание одной группы через несколько оснований не создаёт дополнительных прав.
- Ручное назначение сохраняется после смены кафедры группы.
- При удалении кафедрального разрешения ручное назначение той же группы остаётся действующим.
- Группа без кафедры не входит в условную кафедру «Все» или «Без кафедры». Разрешение на неё назначается только вручную.
- Доступ проверяется к активным объектам текущего набора расписания; устаревшие привязки не дают прав.

### 4.3. Правило изменения занятия

Для редактора операция допустима, если у занятия есть хотя бы одна группа и ВСЕ его группы входят в разрешённый набор.

При создании проверяется новый состав. При редактировании проверяются исходный и новый составы. При удалении и переносе проверяется исходный состав. При отмене проверяются текущее состояние и восстанавливаемый состав.

Примеры:

| Ситуация | Результат |
|---|---|
| Разрешённая группа, преподаватель другой кафедры, чужая аудитория | Редактирование разрешено |
| Чужая группа в аудитории своей кафедры | Только просмотр |
| Поток из двух разрешённых групп | Редактирование разрешено целиком |
| Поток из разрешённой и чужой группы | Только просмотр целиком |
| Занятие без группы | Только просмотр для редактора |
| У своей пары пытаются заменить группу на недоступную | Отказ без изменений |
| У чужой пары пытаются заменить группу на свою | Отказ без изменений |

### 4.4. Изменение разрешений во время работы

- Источник истины — актуальные серверные данные, а не список, полученный при входе.
- Изменение прав увеличивает версию разрешений. Смена кафедры группы также делает затронутые разрешения неактуальными.
- Следующий запрос выполняется уже с новыми правами, даже если вкладка открыта давно.
- Сохранение из ранее открытой формы после отзыва доступа возвращает отказ и обновляет интерфейс.
- Блокировка учётной записи и сброс пароля аннулируют её действующие сессии.

## 5. Интерфейс управления пользователями

### 5.1. Список пользователей

Доступен только администратору. Столбцы: логин, имя сотрудника, состояние, кафедры, число ручных назначений, итоговое число разрешённых групп. Действия: создать, изменить имя/права, сбросить пароль, заблокировать/разблокировать.

Логин после создания не переименовывается в первой версии. Имя сотрудника можно менять. История сохраняет стабильный идентификатор автора и подпись автора на момент действия.

### 5.2. Создание и редактирование

Форма создания содержит:

1. Логин.
2. Пароль и его подтверждение.
3. Необязательное имя сотрудника.
4. Выбор нескольких кафедр с поиском.
5. Ручной выбор групп с поиском и фильтром по кафедре.
6. Итоговый список групп с основаниями доступа: «Кафедра …», «Вручную» либо оба основания.

Фильтр по кафедре в ручном списке только фильтрует список: сам по себе он не выдаёт доступ ко всей кафедре. Выбор кафедрального разрешения находится в отдельном явно подписанном блоке.

Если итоговый список пуст, форма сообщает «Пользователь сможет только просматривать расписание», но позволяет сохранить пользователя.

Сохранение учётной записи и её начальных прав атомарно: нельзя получить созданного пользователя с потерянной половиной назначений.

### 5.3. Валидация и пароль

- Для новых логинов: 3–64 символа из латинских букв, цифр, точки, дефиса и подчёркивания. Пробелы по краям удаляются; сравнение без учёта регистра. Уникальность обеспечивается хранилищем, включая одновременное создание.
- Существующий логин администратора сохраняется при миграции даже при несоответствии новому формату; нормализованный вариант резервируется от повторного использования.
- Для новых паролей: минимум 8 символов, максимум 72 байта UTF-8 при использовании существующего bcrypt. Пароль не обрезается и не нормализуется; превышение лимита вызывает понятную ошибку.
- Пароль и подтверждение должны совпадать. Хранится только хеш; хеши и пароли не выдаются API и не попадают в журнал.
- Сброс пароля выполняет администратор; самостоятельная смена требует текущий пароль.
- После самостоятельной смены пароля также завершаются все сессии пользователя, включая текущую; интерфейс направляет на повторный вход.
- Ошибка входа одинаковая для неизвестного логина, неверного пароля и заблокированного пользователя.
- Защита от перебора учитывает нормализованный логин и IP: максимум 10 неуспешных попыток на логин и 100 на IP за скользящие 15 минут. По достижении любого порога дальнейшие попытки получают `429` до освобождения окна; успешные входы не увеличивают счётчики. Значения вынести в константы и покрыть тестами. Неизвестные логины учитываются тем же способом; просроченные записи счётчиков удаляются.
- Существующая CSRF-защита сохраняется для новых команд. Логины, имена и подписи истории выводятся как текст с экранированием, а не как пользовательский HTML.

## 6. Поведение расписания

### 6.1. Начальный экран и навигация

- После входа открывается представление групп с фильтром «Мои группы».
- При наличии групп выбирается первая разрешённая группа в существующей естественной сортировке названий.
- При отсутствии разрешённых групп показывается сообщение о режиме просмотра и доступен переход к общему списку.
- Переключатель «Все группы» позволяет просматривать чужое расписание, не меняя прав.
- Переключение вида, недели, семестрового/недельного отображения не расширяет права. Операции глобального переключения рабочего набора данных остаются административными.

### 6.2. Свои и чужие занятия

- Свои занятия сохраняют обычное отображение и доступные действия.
- Чужие занятия получают приглушённый фон/рамку, значок замка и текстовую подсказку «Только просмотр — нет доступа ко всем группам занятия».
- Значение цветов дисциплин сохраняется. Недоступность обозначается не только цветом.
- Заблокированы перетаскивание, удаление, сохранение формы, контекстные команды и клавиатурные способы изменения чужого занятия.
- Открыть карточку чужого занятия для чтения можно.
- Для смешанного потока карточка перечисляет группы, из-за которых редактирование недоступно.
- Признак доступности и причина поступают с сервера. Клиентская логика не является защитой.
- Печать и экспорт не добавляют служебные замки и затемнение к самому расписанию.

### 6.3. Создание занятия из любого места

Во всех представлениях есть общая кнопка «Добавить занятие». В представлениях с календарной ячейкой доступно также добавление из ячейки.

| Контекст | Предзаполнение |
|---|---|
| Разрешённая группа | Группа и известные из контекста дата/неделя/пара |
| Чужая группа | Группа не подставляется; пользователь выбирает разрешённую группу |
| Аудитория | Аудитория и известные дата/неделя/пара |
| Преподаватель | Преподаватель и известные дата/неделя/пара |
| Кафедра, сводка, другое представление | Только однозначно известные параметры; группа выбирается явно |

- В списке групп формы доступны только разрешённые группы, включая множественный выбор для потока.
- Преподаватели и аудитории выбираются из общего справочника, включая другие кафедры. Отсутствующий объект редактор не создаёт через ввод произвольного имени.
- Предзаполненные поля можно менять, соблюдая права по группам и обычные проверки расписания.
- Если время не определяется контекстом, пользователь задаёт его в форме; оно не выбирается молча.
- Добавление из занятой ячейки не заменяет существующее занятие. При конфликте сохранение отклоняется с объяснением.
- Если разрешённых групп нет, кнопка недоступна и поясняет причину.
- Если созданное занятие не попадает в текущий фильтр, сообщение об успехе содержит переход к нему.

## 7. Матрица операций первой версии

| Операция | Редактор | Администратор |
|---|---|---|
| Просмотр рабочего расписания, проверок и общего журнала переносов | Да | Да |
| Печать и обычный экспорт расписания | Да | Да |
| Создание, редактирование, удаление занятия | Только разрешённые группы | Да |
| Перенос, изменение аудитории/преподавателя, перенос экзамена | Только разрешённые группы | Да |
| Отправка отдельного занятия в буфер и размещение из буфера | Только разрешённые группы | Да |
| Установка/снятие блокировки отдельного занятия | Только разрешённые группы; блокировка не расширяет права | Да |
| Адресная отмена переноса | Только собственное действие и при текущих правах | Любое выбранное действие с проверками |
| Общий старый откат других изменений | Нет | Да, с защитой от неактуальных данных и с аудитом |
| Массовая замена преподавателя, удаление расписания сущности | Только если весь результат затрагивает разрешённые группы | Да |
| Подбор аудиторий, разгрузка пар, размещение/очистка СР | Только в явно выбранном разрешённом наборе; проверяется полный результат | Да |
| Блокировка времени преподавателя, вывод аудитории, отпуск/мероприятие | Только если операция выражается занятиями разрешённых групп и не меняет общие настройки ресурса; иначе отказ | Да |
| Очистка всего буфера, нераспределённых занятий, всей базы или расписания | Нет | Да |
| Изменение справочников, скрытие сущностей для всех, кафедральная принадлежность | Нет | Да |
| Учебные планы, связи дисциплин, алиасы, настройки семестра/системы | Только чтение нужных для просмотра данных | Да |
| Импорт, архивы и скачивание файла базы, восстановление | Нет | Да |
| Публикация, гостевые настройки | Нет | Да |
| Редактирование/удаление записей аудиторской истории | Нет | Нет через интерфейс или обычный API |

Каждый существующий маршрут должен получить одну конкретную строку этой матрицы. Если операция не может вычислить и проверить полный набор своих изменений, для редактора она закрывается до доработки; релиз не считается завершённым, если это относится к операции, обещанной редактору в таблице.

Глобальная очистка журнала переносов заменяется фильтрами отображения. Примечание к записи, если сохраняется как функция, изменяется отдельным аудируемым действием, без переписывания исходного события.

## 8. Массовые и косвенные изменения

Для каждой операции используется последовательность:

1. Загрузить актуального пользователя и его разрешения.
2. Вычислить полный набор предполагаемых изменений: выбранные занятия, связанные потоки, изменения тем, вытеснение/замены, вспомогательные записи.
3. Проверить права по всем затронутым занятиям и исходным/новым группам.
4. Проверить версии и конфликты ресурсов по всему расписанию, включая чужие группы.
5. В одной транзакции сохранить изменения, версии и записи журнала.
6. После успешного завершения вернуть точный результат и идентификатор действия.

Нельзя частично выполнить массовую операцию и молча пропустить чужие занятия. Если найдена недоступная часть, вся команда отклоняется и сообщает причину.

Предпросмотр не является разрешением на последующее применение: при применении всё проверяется повторно. Если набор изменений после предпросмотра изменился, возвращается конфликт и требуется новый предпросмотр.

Автоматическая сортировка тем в текущем коде запускается после изменений. Её результат должен войти в ту же проверку прав и ту же транзакцию; недостаточно проверить только переносимую пару. Если необходимая сортировка затронет недоступные занятия, исходная операция отклоняется целиком.

## 9. Общий журнал и точная персональная отмена

### 9.1. Структура действия

Каждая команда переноса получает уникальный `actionId`. Повтор сетевого запроса с тем же ключом идемпотентности возвращает исходный результат, а не переносит занятие второй раз.

Сохраняются:

- `actionId`, тип действия и время сервера в UTC;
- идентификатор автора и его подпись на момент действия;
- идентификатор поколения данных расписания;
- стабильные идентификаторы всех затронутых занятий;
- группы, преподаватели, аудитории и положение до/после;
- необходимые для отмены состояния связанных записей;
- версии затронутых записей после выполнения;
- ссылка `revertsActionId` для отмены;
- ключ идемпотентности команды.

Для массового переноса одно действие может включать несколько занятий. Оно отменяется целиком. Частичная отмена одного занятия из такой команды не поддерживается. Операции управления пользователями не смешиваются с журналом переносов и фиксируются в отдельном аудите.

### 9.2. Что показывает журнал

- Единый список действий всех пользователей, доступный всем вошедшим сотрудникам.
- Поиск/фильтры по автору, группе, занятию, дате и состоянию отмены; по умолчанию видны действия всех авторов.
- Время отображается в часовом поясе приложения, хранится в UTC.
- Переносы после публикации и до публикации не образуют разные журналы; журнал относится к рабочим действиям.
- Отмена создаёт отдельное событие со ссылкой на исходное действие. Исходная запись остаётся видимой и получает вычисляемую отметку об отмене.
- Старые записи без автора показываются как «Автор не указан — запись до обновления». Им не назначается вымышленный автор.
- Старые записи без достаточных снимков и версий недоступны для новой адресной отмены.

### 9.3. Три места кнопки отмены

1. **Сообщение после переноса:** хранит `actionId` только что выполненной команды. Любые последующие действия других пользователей не подменяют этот идентификатор.
2. **Общая кнопка «Отменить мой последний перенос»:** сервер выбирает последний ещё не отменённый перенос текущего пользователя в текущем поколении расписания. Кнопка показывает описание и отправляет конкретный `actionId`. Если это действие уже нельзя отменить, она показывает причину и не переключается молча на более старое действие.
3. **Строка общего журнала:** отменяет именно выбранную запись. Редактору доступна только у собственных действий, администратору — у любых действий с достаточными данными для безопасной отмены.

Перед подтверждением указываются группа/группы, предмет, откуда и куда будет возвращено занятие; для массового действия — число занятий и список затрагиваемых групп.

### 9.4. Алгоритм отмены

В одной транзакции сервер:

1. Проверяет активную сессию и действующие права.
2. Находит действие по `actionId`, проверяет автора для редактора и соответствие текущему поколению расписания.
3. Проверяет, что действие не отменено ранее.
4. Загружает все затронутые записи и сравнивает их версии с ожидаемым состоянием после исходной команды.
5. Проверяет доступ ко всем текущим и восстанавливаемым группам.
6. Проверяет восстановление на накладки групп, преподавателей и аудиторий, вместимость и остальные действующие ограничения. Учитывает весь восстанавливаемый набор как одну операцию.
7. Восстанавливает полный результат исходной команды, включая её изменения тем и связей, увеличивает версии и добавляет запись об отмене.

Если любой шаг не проходит, ни одна запись расписания или истории не меняется. Отмена не должна заново запускать несвязанную глобальную сортировку, меняющую посторонние занятия.

### 9.5. Одновременная работа

| Последовательность | Ожидаемый результат |
|---|---|
| А переносит X; Б переносит Y; А отменяет свой перенос X | Возвращается X; Y не меняется |
| А переносит X; Б изменяет X; А отменяет свой перенос | Отказ: занятие изменено после переноса |
| А переносит X; Б занимает исходное место X | Отказ с описанием конфликта; занятие Б не вытесняется |
| А переносит X; администратор отзывает права А на его группу | Отказ по актуальным правам |
| Две вкладки одновременно отменяют одно действие | Только одна отмена и одно событие отмены; повтор получает результат уже выполненной отмены |
| А переносит X дважды и пытается отменить первый перенос | Отказ из-за более позднего изменения |
| А отменил второй перенос X и хочет отменить первый | В первой версии цепочечная отмена через пересчёт старых версий не поддерживается; старое действие остаётся недоступным, даже если положение визуально совпало |
| Перенос затронул сортировку тем другого занятия, затем это занятие изменили | Отказ от всей отмены, без частичного восстановления |
| Занятие удалено либо восстановлен архив | Старое действие не восстанавливает занятие автоматически; отмена недоступна |

Отмену самой отмены отдельной кнопкой «Повторить» в первой версии не добавляем. Новое перемещение выполняется обычной командой переноса.

## 10. Хранение, миграция и восстановление

### 10.1. Разделение хранилищ

Учётные записи, хеши паролей, разрешения и аудит управления доступом размещаются в отдельной служебной SQLite-базе, которая не подменяется при восстановлении архива расписания.

Расписание, его версии, команды переносов и события отмены хранятся вместе, чтобы запись расписания и истории была атомарной. Текущий журнал для интерфейса может быть проекцией новой истории, но не единственным источником данных для отмены.

Полная резервная копия включает служебную базу, базу расписания и необходимую конфигурацию. Архив расписания не должен содержать пароли и назначения прав. Восстановление только расписания не откатывает учётные записи и аудит доступа.

### 10.2. Идентичность объектов

- Пользователи, кафедры, группы и действия получают стабильные идентификаторы, не зависящие от отображаемого имени.
- Назначение ручного доступа не привязывается только к переиспользуемому числовому ID или совпадению имени.
- Переименование существующей группы сохраняет её идентичность и права.
- Новая группа с тем же названием после удаления старой не наследует ручные разрешения.
- Импорт, обновляющий существующую группу, сохраняет её идентичность и подтверждённую кафедру. Неоднозначное сопоставление не считается совпадением и требует административного решения.
- Подтверждённая принадлежность группы для доступа не перезаписывается произвольными данными импорта или старого архива.
- При восстановлении архива сохраняются только проверяемые привязки к известным стабильным идентификаторам. Неизвестные/старые объекты без идентификаторов не получают права по совпадению имени; администратору выводится список для сопоставления.
- Восстановление архива, полная очистка и замена расписания создают новое поколение данных. Все прежние команды отмены становятся недействительными, даже если числовые ID совпали.

### 10.3. История и архивы

Перед восстановлением архива текущая база и её история сохраняются существующим механизмом страховочного архива. После восстановления рабочий журнал соответствует восстановленному расписанию; новая запись восстановления указывает прежнее и новое поколения данных. История заменённого набора остаётся в страховочном архиве для администратора, а не смешивается с текущим рабочим журналом.

Таким образом, «общий журнал» означает общий для всех сотрудников текущего рабочего набора, а не безусловное объединение несовместимых историй разных восстановлений.

### 10.4. Миграция существующей установки

1. Сделать резервную копию конфигурации и расписания.
2. Создать служебное хранилище и новую схему расписания.
3. Однократно перенести существующего администратора, сохранив логин и хеш пароля. Секрет сессий и пароль подтверждения очистки не превращать в обычные пользовательские учётные записи.
4. Проверить работоспособность нового источника авторизации, записать маркер завершённой миграции. Повторный запуск не создаёт второго администратора и не возвращает старый пароль.
5. Удалить использование старой пары логин/хеш как альтернативного способа входа. Устаревшие поля удалять только после успешной миграции и при наличии резервной копии.
6. Завершить старые сессии с флагом `isAdmin`: они не должны автоматически получить новую роль без входа.
7. Выключить анонимное редактирование и убрать соответствующий переключатель из обычного интерфейса.
8. Подготовить подтверждение кафедральной принадлежности групп. До назначения прав обычные пользователи не получают доступ к записи автоматически.

При сбое миграции запуск не должен продолжаться в частично включённой модели прав. Откат выполняется на согласованную резервную копию и предыдущую версию приложения.

## 11. Серверный контракт и границы изменений

Предлагаемые новые маршруты, фиксируемые как целевой контракт:

| Маршрут | Назначение | Доступ |
|---|---|---|
| `GET /api/users` | Список учётных записей без секретов | Администратор |
| `POST /api/users` | Создание редактора с начальными правами | Администратор |
| `PATCH /api/users/:id` | Имя и состояние учётной записи | Администратор |
| `PUT /api/users/:id/permissions` | Атомарная замена кафедральных и ручных назначений | Администратор |
| `POST /api/users/:id/password-reset` | Задание нового пароля и отзыв сессий | Администратор |
| `GET /api/me/permissions` | Актуальная роль, версия прав и разрешённые группы | Вошедший пользователь |
| `GET /api/move-actions/latest-own` | Последний неотменённый перенос пользователя и доступность отмены | Вошедший пользователь |
| `POST /api/move-actions/:actionId/revert` | Адресная идемпотентная отмена | Автор либо администратор |

Существующие маршруты входа, проверки входа и смены собственного пароля адаптируются к пользователям. Ответ проверки входа различает факт входа и роль; обычный вошедший пользователь больше не считается администратором.

Существующие маршруты изменения расписания сохраняют назначение, но получают обязательные проверки доступа, ожидаемых версий и контекст автора. Старые маршруты отмены не могут оставаться обходным путём новой проверки.

Коды ответов:

- `400`: некорректная форма или отсутствующие обязательные данные команды;
- `401`: нет действующей авторизации;
- `403`: недостаточно прав;
- `404`: объект или действие не существует;
- `409`: устаревшая версия, несовместимое состояние, конфликт расписания или занятый логин;
- `429`: превышен лимит попыток входа.

Отказы имеют машинный код причины и русское сообщение. Для конфликтов возвращаются данные, достаточные для обновления формы, но не секреты авторизации.

Для одной и той же идемпотентной команды повтор с тем же телом возвращает прежний результат; повтор ключа с другим телом отклоняется. Ключ связан с пользователем и типом операции.

Изменение имени, состояния и разрешений пользователя также передаёт ожидаемую версию записи. Если администратор открыл две формы и одна уже сохранена, вторая получает `409`, а не затирает более новое назначение. Идентификатор автора любой команды берётся только из проверенной серверной сессии; присланное клиентом авторство не принимается.

Операции пользователей и прав исключаются из текущего механизма `finalizeMutation`: они не сортируют темы, не отмечают расписание неопубликованным и не меняют версию расписания. Для прав используется отдельная версия.

## 12. Дорожная карта реализации

Этапы выполняются в указанном порядке. У каждого этапа есть проверяемый результат; формулировка «добавить проверку» без перечисления защищённых операций не является выполнением задачи.

### Этап 1. Инвентаризация и таблица покрытия

Задачи:

- Перечислить все HTTP-маршруты чтения/записи и вызываемые сервисные команды.
- Для каждого указать роль, правило по группам, полный набор косвенных изменений и соответствующий тест.
- Отдельно включить гостевую запись, экспорт POST-запросами, буфер, экзамены, потоковые занятия, автоматические подборы, сортировку тем, старые отмены и архивы.
- Зафиксировать место хранения подтверждённой принадлежности групп и устойчивых идентификаторов; оно не должно зависеть от восстановленного значения `dept` без проверки.

Результат: отдельная таблица покрытия маршрутов, по которой нельзя оставить незащищённую команду вне списка.

Приёмка: каждому маршруту назначена строка матрицы операций и способ проверки. Все действующие пути обхода перечислены.

### Этап 2. Схема данных и миграция

Задачи:

- Создать служебную базу пользователей и разрешений, стабильные идентификаторы объектов, версии и поколения данных.
- Реализовать повторяемую миграцию администратора и инвалидировать старые сессии.
- Разделить резервное копирование всей установки и архивирование расписания.
- Добавить подготовку/подтверждение принадлежности групп кафедрам.

Результат: установка обновляется без потери администратора и расписания; восстановление расписания не возвращает старые пароли.

Приёмка: миграция проверена на копии старой базы, повторном запуске и искусственном сбое; рабочая пользовательская база для тестирования не используется.

### Этап 3. Авторизация и управление пользователями

Задачи:

- Разделить «вошёл», «администратор» и «может изменить занятие».
- Реализовать API пользователей, форму управления, уникальность логинов и валидацию паролей.
- Реализовать изменение прав, блокировку, сброс/смену пароля и отзыв сессий.
- Добавить аудит управления учётными записями, отдельную версию прав и защиту от перебора.

Результат: администратор создаёт редактора с точным списком разрешённых групп; редактор может войти, но не получает административных функций.

Приёмка: ошибки формы и дубли не оставляют частично созданных данных; обычный пользователь не может изменить роль, права или чужой пароль прямым запросом.

### Этап 4. Единые проверки операций расписания

Задачи:

- Реализовать единый сервис разрешений по всем группам занятия.
- Защитить одиночные и массовые команды, создание, буфер, экзамены и косвенные изменения.
- Сделать ожидаемые версии обязательными для записи существующих занятий; одного глобального `dataVersion` для защиты от потери правок недостаточно.
- Закрыть гостевую запись и все альтернативные маршруты обхода.
- Проверять конфликты по всему расписанию, а не только по своим группам.

Результат: изменение вне разрешённых групп невозможно через любой существующий API.

Приёмка: для каждой команды есть положительный и отрицательный интеграционный сценарий; отрицательный сравнивает состояние базы до/после, включая косвенные записи.

### Этап 5. История переносов и персональная отмена

Задачи:

- Добавить авторство, уникальные действия, состояния до/после, версии и идемпотентность переносов.
- Записывать перенос и его историю в одной транзакции.
- Реализовать адресную отмену, повторные проверки и отдельное событие отмены.
- Перевести сообщение после переноса, общую кнопку и строки журнала на `actionId`.
- Адаптировать старые маршруты/проекции журнала, исключить удаление аудиторской истории при отмене.

Результат: действие А отменяется независимо от более позднего несвязанного действия Б; изменения того же занятия защищены.

Приёмка: проходят все сценарии таблицы одновременной работы из раздела 9.5, включая разные вкладки, общий поток и косвенное изменение темы.

### Этап 6. Интерфейс редактора во всех представлениях

Задачи:

- Добавить стартовый фильтр «Мои группы» и просмотр всех групп.
- Отображать недоступные занятия с замком и объяснением во всех видах, включая недельный, семестровый, преподавателей, аудиторий и сессию.
- Отключить все способы изменения недоступных занятий.
- Добавить создание из любого представления с предзаполнением по разделу 6.3.
- Обрабатывать отзыв прав, истечение сессии и конфликт версии без ложного сообщения об успехе.
- Обновить общий журнал с авторами, фильтрами и точной отменой.

Результат: интерфейс соответствует серверным правилам и объясняет недоступность операции.

Приёмка: браузерные сценарии подтверждают одинаковые права на одну пару во всех представлениях; печать остаётся без служебного затемнения.

### Этап 7. Комплексная проверка и выпуск

Задачи:

- Выполнить матрицу приёмки ниже, существующие тесты и линтер.

- Обновить README: роли, назначение кафедр/групп, поведение потоков, журнал, отмена, резервное копирование.
- Подготовить краткую инструкцию администратору и редактору.
- Перед обновлением рабочей установки сохранить резервную копию; после обновления проверить вход администратора и тестового редактора.

Результат: функция готова к использованию несколькими сотрудниками одновременно, а восстановление и ограничения документированы.

Приёмка: все обязательные сценарии проходят, отсутствуют маршруты без назначенной политики, администратор не потерял действующие функции.

## 14. Граница готовности

Работа завершена только тогда, когда:

1. Администратор создаёт пользователя и получает точно показанный в форме набор разрешённых групп.
2. Пользователь может управлять любым занятием своих групп независимо от кафедр преподавателей и аудиторий.
3. Нельзя изменить чужое занятие ни из интерфейса, ни прямым запросом, ни через массовое действие или отмену.
4. Общий журнал показывает авторство; отмена возвращает конкретное действие, не затрагивая несвязанные действия других пользователей.
5. Изменения той же пары, занятость исходного места, отзыв прав и устаревшие архивные идентификаторы приводят к понятному отказу без частичной записи.
6. Миграция, повторный запуск и восстановление проверены на изолированных данных; вся матрица приёмки выполнена.

Не входят в первую версию: отдельные права по преподавателям/аудиториям, исключения из кафедрального разрешения, саморегистрация, делегирование прав редакторами, частичное разделение потока, принудительная отмена поверх новых изменений, цепочечный undo/redo и отмена удаления через старые неподтверждённые снимки.
