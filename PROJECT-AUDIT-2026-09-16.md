Замечания по зависимостям и безопасности

Аудит npm сам по себе не определяет достижимость проблем. Например, найденное обращение ExcelJS к uuid использует v4 (`node_modules/exceljs/lib/xlsx/xform/sheet/cf-ext/cf-rule-ext-xform.js:1`), а advisory uuid описывает другие функции с переданным буфером. Поэтому откат ExcelJS ради исчезновения строки отчёта не обоснован. Сначала обновить непосредственно используемый Multer и совместимые HTTP-зависимости, затем разобрать транзитивные цепочки.

В проекте уже есть bcrypt, CSRF, httpOnly/SameSite-cookie, helmet, ограничение входа и проверка авторизации перед импортом. Наличие строк innerHTML само по себе не доказательство XSS: во многих местах есть экранирование. В аудит не включено необоснованное утверждение об XSS или SQL-инъекции.

Смена пароля сейчас не отзывает остальные сессии, вход не регенерирует идентификатор сессии (`src/routes/auth.js:47`, `:75`). Это задачи усиления управления сессиями. Значения реальных паролей в ходе аудита не проверялись и не выводились.

Документация Express прямо связывает доверие forwarded-заголовкам с действительной схемой проксирования: [Express behind proxies](https://expressjs.com/en/guide/behind-proxies/).

Для этапа 1 завести отдельные небольшие задачи: `FIX-MIGRATION-ORDER`, `FIX-LESSON-SLOT-VALIDATION`, `FIX-PROXY-TRUST`, `UPDATE-RUNTIME-DEPS`, `FIX-WEEK-NAVIGATION`, `ISOLATE-WIDGET-BUILD`. Каждая содержит воспроизведение, исправление, проверку и самостоятельную запись в истории релиза.

Ключевые решения реализации

- Миграции: таблица `schema_migrations`, уникальный номер, проверка до запуска, транзакция шага; при ошибке не оставлять частично открытое соединение в глобальном `db`. Для старых архивов заранее выполнять пробное обновление временной копии.
- Восстановление: проверка структуры, `quick_check`/`integrity_check` по выбранной процедуре и внешних ключей, миграция копии, переключение и проверка работоспособности. Возврат должен покрывать не только ошибку копирования, но и ошибку после замены файла.
- Публикация: `publicationId`, `datasetId`, `sourceRevision`, `schemaVersion`. Подготовить отдельный каталог версии с JSON и gzip, проверить их, затем переключить ссылку активной версии. Проверить поведение переключения на Windows. При невозможности публикации сохранить предыдущую доступной и показать ошибку.
- Гостевые правки: сервер проверяет принадлежность ID активной публикации и её набору данных. Решение, применять ли их сразу или через согласование, оформить как явную настройку продукта. База и файлы не образуют общую транзакцию автоматически: нужен протокол состояний и повторяемое завершение публикации.
- Операции: перенос/правка → проверка ожидаемой ревизии → доменные проверки → изменение → темы/журнал/undo → увеличение ревизии → commit → ответ. Вынесение сортировки из `res.finish` требует адаптации `sortTopics`, которая сейчас сама открывает транзакции; простое перемещение вызова создаст вложенные BEGIN.
- Общая валидация: дни, целые номера пар и недель, допустимые типы, длины текстов, списки сущностей, неизвестные поля. Различать технический слот буфера и видимый слот расписания. Перед CHECK-ограничениями проверить совместимость уже существующих данных.
- Совместная работа: `datasetId` меняется при подмене базы; `revision` сохраняется устойчиво; `operationId` предотвращает повторное применение повторно отправленного запроса. У undo — ожидаемый ID вершины и сведения об авторе; индивидуальную отмену нельзя реализовать простым фильтром по пользователю без проверки зависимых изменений.
- Производительность: сначала профилирование на синтетическом наборе сопоставимого размера и наборе ×5. Измерять p95 обычных API, задержку основного цикла Node, память, время импорта и отрисовки. Численные цели согласовать после первого замера; сокращение строк файла само по себе не доказывает ускорение.
- Вынесенный worker получает снимок/данные, возвращает предложения; запись в рабочую SQLite выполняется через контролируемый путь с повторной проверкой ревизии. Не создавать несколько независимых писателей с несогласованными кэшами.
- Выпуск: отдельный чистый каталог релиза, установка из lock-файла, манифест и контрольные суммы; серверные настройки отдельно от кода. Проверять сохранность `data`, JSON и gzip публикации при обновлении. Автозапуск, Node, WebView2 и шаблоны Excel входят в сценарий приёмки Windows.

Показательный конфликт с готовыми примерами: Timefold рассматривает одновременное занятие аудитории как жёсткое ограничение, а этот проект допускает его после подтверждения. При интеграции необходимо явно сохранить различие между запретом для человека/группы и предупреждением для аудитории. СР, ЭкзС, ФП и потоковые занятия также требуют нашей модели.

Для объяснений полезен подход Timefold: разложить итоговую оценку по правилам и объектам, показывать вклад каждого конфликта. См. [описание анализа оценки в ветке 1.x](https://docs.timefold.ai/timefold-solver/1.x/constraints-and-score/understanding-the-score). Однако в 2.x `ScoreAnalysis` перенесён в Enterprise Edition: это прямо указано в [руководстве перехода](https://docs.timefold.ai/timefold-solver/latest/upgrading-timefold-solver/upgrade-from-v1). В бесплатном локальном пилоте предусмотреть собственный отчёт причин; не считать все показанные возможности доступными в открытой редакции.

Пример предлагаемого экрана оптимизации: «Вариант А: убрать два окна, изменить три занятия; вариант Б: сохранить все аудитории, убрать одно окно». Это пример дизайна, а не измеренный результат проекта или обещание решателя. Для каждого варианта показывать затронутые группы/преподавателей, предупреждения, фиксированные занятия и возможность полного отката.

Первыми продуктовыми улучшениями после исправлений я бы выбрал предварительный отчёт импорта, сравнение публикаций и объяснение предложений оптимизатора. Они непосредственно уменьшают число ошибочных действий и время проверки расписания. Полную генерацию с нуля, смену SQLite и массовое переписывание интерфейса оценивать только после замеров и проверки пользы пилота.
