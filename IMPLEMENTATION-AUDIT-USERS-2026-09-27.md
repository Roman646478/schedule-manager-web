# Аудит внедрения пользователей и прав

Дата проверки: 27 сентября 2026 года.

## Реализованный результат

- Администратор создаёт и блокирует редакторов, сбрасывает пароль, назначает
  несколько кафедр и отдельные группы. Изменение пользователя выполняется одной
  транзакцией и защищено версией строки.
- Пользователи, права и сессии хранятся в отдельной `access.db`. Восстановление
  архива расписания их не откатывает.
- Ручное право связано со стабильным `groups.access_uid`. Удаление группы и
  создание новой с прежним именем не передаёт ей старое право.
- Все вошедшие пользователи видят рабочее расписание целиком. Сервер разрешает
  запись только тогда, когда доступны все группы занятия. Вид группы,
  преподавателя или аудитории на решение не влияет.
- Смешанный поток целиком доступен только для чтения. Чужие карточки выделены,
  не перетаскиваются, не имеют кнопок сохранения, удаления и блокировки.
- Редактор создаёт занятие из любого представления только для своих групп и
  выбирает существующие дисциплины, аудитории и преподавателей.
- Безопасные массовые команды проверяют полный выбранный набор: замена
  преподавателя, подбор аудиторий, разгрузка четвёртой пары, удаление расписания
  сущности и отпуск группы. Если хотя бы одно занятие недоступно, команда целиком
  отклоняется.
- Системные операции без явного ограниченного набора групп остаются
  административными: импорт, публикация, архивы, справочники, очистки,
  расстановка СР по всей неделе, вывод аудитории и блокировка времени ресурса.
- Старое гостевое редактирование окончательно выключено. Гость читает только
  опубликованный снимок.
- Общий журнал показывает автора, исходное и итоговое место, состояние и автора
  отмены. Старые строки показываются как история без вымышленного автора.
- Каждый перенос получает UUID команды. Повтор запроса с тем же UUID возвращает
  прежний результат без второй мутации.
- Отмена выполняется по выбранному `actionId`, а не по последней строке журнала.
  Редактор отменяет только своё действие, администратор — выбранное действие
  любого пользователя.
- Отмена сравнивает ревизии основного занятия, всех строк многопарного экзамена
  и косвенно переставленных тем. Изменение любой из них запрещает весь откат.
- Восстанавливаются занятие, вытесненная СР, цепочка старого журнала и темы.
  Двойная отмена даёт конфликт и не создаёт второе событие.
- После восстановления архива меняется поколение расписания. Команды из другого
  поколения остаются историей, но не могут изменить восстановленные данные.
- При аварии между фиксацией команды и HTTP-ответом незавершённая запись
  финализируется при следующем запуске.

## Найденные и закрытые риски

1. **Глобальная отмена могла снять чужое действие.** Редакторам закрыт старый
   стек Undo; добавлены персональный последний перенос и отмена выбранной строки.
2. **Проверка только интерфейсом.** Введена единая серверная политика небезопасных
   маршрутов и повторная проверка актуальных прав непосредственно в транзакции.
3. **Поток мог дать доступ через одну свою группу.** Условие заменено на
   `все группы занятия входят в доступ` для карточек, прямых запросов и массовых
   команд.
4. **Устаревшая вкладка могла затереть новую правку.** Перенос, редактирование,
   удаление, блокировка и буфер проверяют `expectedRevision`.
5. **Сетевой повтор мог перенести пару дважды.** Добавлен идемпотентный UUID
   команды и проверка владельца/занятия при повторе.
6. **Редактор мог создать справочную сущность произвольной строкой.** Сервер
   разрешает редактору только существующие аудитории, преподавателей и
   дисциплины; мероприятия создаёт только администратор или ограниченная
   команда отпуска своей группы.
7. **Сортировка тем могла незаметно изменить чужой поток.** Перед фиксацией
   проверяется каждое занятие, которое будет пересортировано; вся исходная
   команда откатывается при недоступном занятии.
8. **Отмена не учитывала косвенные изменения.** В снимок действия включены
   затронутые СР, многопарные формы контроля, темы и старое состояние журнала.
9. **Архив расписания мог откатить пароль или оживить старую отмену.** Данные
   доступа вынесены отдельно, а отмены привязаны к поколению расписания.
10. **Блокировка пользователя не отзывала открытую вкладку.** Каждый запрос
    сверяет `active` и `auth_version`; блокировка и смена пароля инвалидируют
    старые сессии.
11. **Поиск ручных групп в форме мог стереть скрытые фильтром отметки.** Выбор
    хранится независимо от отфильтрованной части списка.
12. **Строчное редактирование таблицы преподавателя обходило признаки доступа и
    ревизии.** Поля чужих строк стали текстом, кнопка переноса скрыта, сохранение
    отправляет текущую ревизию.

## Проверки

- ESLint по всему репозиторию.
- 437 модульных и интеграционных тестов полного набора — все пройдены.
- Отдельная матрица API прав: просмотр чужого, смешанный поток, отзыв сессии,
  стабильная идентичность группы, запрет новых справочников, конфликт сортировки,
  параллельные переносы, чужой `actionId`, двойная отмена и сетевой повтор.
- 15 браузерных сценариев Playwright: вход, импорт, перенос, отмена, публикация,
  гостевой экран, Excel и печать — все пройдены. Дополнительно устранена гонка
  теста после входа: сценарий теперь ждёт загрузки браузерного API, а не только
  смены URL.
- `npm audit --omit=dev`: известных уязвимостей зависимостей нет.

## Эксплуатационные условия

- Резервная копия пользователей должна включать `data/access.db`. Встроенные
  архивы расписания намеренно содержат только `schedule.db`.
- Для работы по локальной сети следует включить штатный HTTPS, иначе пароль и
  cookie передаются по открытому HTTP.
- Дефолтные пароли `admin/admin` и пароль очистки должны быть сменены после
  первого запуска; интерфейс и журнал сервера сохраняют предупреждение до смены.
